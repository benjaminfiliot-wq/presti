# 014-17 — l'e2e de la suspension (v15 §5)

## Ce qui a été corrigé (ne le modifie pas, prouve-le)

La suspension (table `suspensions`, RPC `suspendre_artisan` / `reactiver_artisan`, migration 0068) coupait l'accès de l'artisan mais **pas son activité** : sa page publique restait ouverte, les nouveaux leads passaient, le moteur répondait, les relances partaient. Une seule lecture de vérité existe désormais, `lib/suspension.ts` (`suspensionEnCours(artisanId)`), lue par `app/p/[slug]/page.tsx` (page neutre « Page indisponible »), `app/api/leads/route.ts` (410, message neutre), `app/api/conversation/route.ts` et `/stream` (`reply: null, indisponible: true`), `app/api/cron/relances/route.ts` (relance sautée, non marquée envoyée : elle repart à la réactivation). La connexion, elle, était déjà refusée (`lib/authArtisan.ts`, code `suspendu`).

## Comment tu écris la suite

Copie le harnais de `scripts/controle-droits-e2e.mjs` et `scripts/controle-apports-e2e.mjs` (lecture de `.env.local`, comptes `susp-<nom>-<st>@presti-test.invalid`, artisan fondateur avec `is_founder`, `session()` + `verifierSessionTest`, `T()`, purge en `finally`, `process.exitCode`). Le geste « suspendre » exige une **re-confirmation** (`lib/direction/reconfirmation.ts` : en-tête `x-presti-reconfirmation`, jeton émis par `emettre(uid, 'artisan')` via la route que l'interface appelle — trouve-la, ne l'invente pas ; à défaut, `emettre()` est appelable depuis le script avec la clé service, comme le fait l'interface côté serveur). Cible : `TEST_BASE` (défaut `https://prestiapp.fr` ; local `http://localhost:3000`). Code 2 si `actionsArtisan` est baissé sur la cible. **Zéro appel IA** (le moteur doit se taire : `reply: null` suffit), aucune donnée réelle, un artisan de test avec un lead de test et une relance planifiée dans le passé (insérée par la clé service).

Ce qu'elle prouve, dans l'ordre :
1. **Avant** : l'artisan de test se connecte (200 sur une route authentifiée), sa page `/p/<slug>` rend 200 sans « Page indisponible », `POST /api/leads` crée un lead, `GET` de la fiche ne montre pas de suspension.
2. **Suspendre** (fondateur, `POST /api/controle/clients/<id>/action` `{ action: 'suspendre', motif, message }` avec re-confirmation) → 200 ; en base : une ligne `suspensions` sans `levee_le` ; une ligne `journal_direction` `artisan_suspendu`.
3. **Effets** : la session de l'artisan est refusée (401/403, code `suspendu`) ; `/p/<slug>` contient « Page indisponible » ; `POST /api/leads` → 410 avec le message neutre ; `POST /api/conversation` sur le lead existant → `reply: null` (et `indisponible: true`) ; `GET /api/cron/relances` (avec le secret du cron, `CRON_SECRET`) laisse la relance **non envoyée** (`envoyee = false`) et ne crée aucun message.
4. **Réactiver** (`{ action: 'reactiver', motif }`) → 200 ; `levee_le` posé ; l'artisan se reconnecte ; `/p/<slug>` rend la page normale ; `POST /api/leads` → 200 ; le cron envoie la relance (ou la marque envoyée) — tout revient.
5. **Garde-fous** : suspendre sans motif → 400 ; suspendre deux fois → 400 « déjà » ; le rôle `lecture` → 403.

Termine par `014-17 : PASS|FAIL — …`, avec la ligne « N réussis, M échoués ».
