## Contexte

**Décision 5 de Benj (25/09)** : durcir l'usine, en retirant au compte `usine` le sudo sans mot de passe et le groupe `docker` une fois l'installation finie.

Codex tourne sur l'usine sous le compte `usine`, **avec le réseau** (les fiches de l'orchestre, `scripts/usine.mjs lancer`). Aujourd'hui, ce compte a `usine ALL=(ALL) NOPASSWD:ALL` (posé par cloud-init dans `/etc/sudoers.d/90-cloud-init-users`) et le groupe `docker`, qui vaut root. Une injection dans une fiche (un texte lu comme une consigne) pourrait donc prendre la machine, lire le coffre des agents ou la connexion Codex de `chef-modele`. Le bac à sable de Codex borne l'écriture, pas la lecture (revue du 25/09, 026-102).

La réponse : un compte **`gardien`**, joignable seulement par une clé du poste (`~/.ssh/presti-usine-gardien`, jamais copiée sur l'usine, jamais utilisée par `usine.mjs` ni par Codex), garde le sudo pour les installations futures ; `usine` le perd. Les règles étroites existantes restent : `presti-coffre` et `presti-journal` sous `agents` (026-050), `presti-chef-modele-essai` sous `chef-modele` (026-148).

**Deux pièges connus** (mémoire `usine-oracle`) : **jamais `ufw`** sur l'usine (il coupe l'accès : les règles d'Oracle passent par `iptables`, qu'on ne touche pas) ; l'IP publique grisée dans la console n'est pas une panne.

Le juge est `scripts/usine-durcie-qa.mjs`, écrit par Claude Code en 026-194.
