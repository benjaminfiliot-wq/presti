## Contexte

Depuis le 24/09, **les agents trouvent, écrivent, envoient, relancent, répondent et qualifient** ; Benj ne prend que les appels et voit arriver les paiements (`SaaS/Produit/Ecosysteme-Rectification-2026-09-24.md` §3.1). Depuis la voie gratuite du 25/09, le premier contact part par le **formulaire de contact du site** de l'entreprise (`formulaire_site`, un par entreprise, à vie), soumis sur l'usine par le porteur de 026-095 après les verdicts du **Facteur** ; les réponses arrivent dans le Gmail de prospection et la suite part de ce Gmail (`email_sollicite`, seulement à qui a écrit). Jamais prestiapp.fr dans un premier contact. Chaque envoi part seulement si trois juges disent oui : **J1** (faits), **J3** (conformité, déterministe) et **un second juge** (ton, promesses) (§3.11). Instagram n'est plus qu'un canal **entrant** : les réponses privées à un commentaire « SITE » et les messages reçus (§3.4 b et c ; décision R5 : aucun message privé Instagram à froid par un agent).

La station (`/controle/station`) montre donc ces envois **en lecture seule**, dans la Salle des envois et dans la barre du haut (« ENVOIS DU JOUR x/plafond · P2 »). Elle vérifie **une seconde fois, en défense**, que chaque envoi parti porte ses trois verdicts ; un envoi sans eux est une anomalie, qui devient une carte Attention rouge (026-070).

**Les règles de volume** (voie gratuite §2), que la base fait respecter (0099, 026-034 ; 0111, 026-063) et que l'écran se contente de montrer :
- le formulaire, en formulaires par jour ouvré : P0 **5**, P1 **10**, P2 **20**, P3 **30**, P4 **40** (plafond des agents ; au-delà, seul Benj) ; un par entreprise, à vie ; jamais relancé ;
- `email_sollicite` : 50 par jour, seulement en réponse à quelqu'un qui a écrit ;
- une technologie de formulaire (Contact Form 7, WPForms…) se met en pause après 3 échecs de soumission d'affilée ;
- **« au vert »** se compte en compteurs absolus : 0 plainte et 0 avis d'abus, au plus 3 STOP sur les 100 derniers envois, moins de 3 échecs de soumission d'affilée, et au moins une réponse positive à partir de P3.

**L'entonnoir** ne compte que les contacts **froids** (les entrants, chauds, n'entrent pas dans le bilan). **Le bilan** (décision R10, réécrite par la voie gratuite §2) porte sur les **100 premiers contacts froids** des agents, partis dès le premier formulaire (au plus tôt le lundi 12/10/2026) ; sa date est celle de la base (`ops.etat_envoi.bilan_le`, 0111 : le lundi qui suit le 100e contact froid, 3 jours au moins après ; le 02/11 au rythme prévu), nulle tant que le formulaire est fermé ; au moins 1 vente ou 4 « oui » → palier P3 ; 1 à 3 « oui » → nouveau message, P2 prolongé ; 0 « oui » → arrêt du froid.

Les données viennent de la base (fonctions de 026-079 réécrite), sous ces formes :
- envois du jour : `{ id, canal, technologie, type: 'premier_contact' | 'relance' | 'lien_maquette' | 'reponse', statut, envoyeur, metier, commune, variante, froid, verdicts: { j1, j3, second }, prepare_le, envoye_le }`, chaque verdict valant `'pass'`, `'refus'` ou `null` ; `technologie` est nulle hors `formulaire_site` ;
- compteurs par canal (`pilotage_compteurs_du_jour()`) : `{ canal, palier, plafond, utilises, plaintes_7j, avis_abus, stop_100, echecs_affilee, reponses_positives }` (`plafond` peut être `null` si le canal n'est pas réglé ; les cinq derniers peuvent valoir `null` tant qu'ils ne sont pas mesurés) ;
- technologies (`pilotage_compteurs_technologies()`) : `{ technologie, envois_jour, echecs_affilee, etat: 'active' | 'pause', pause_motif, envois_300, reponses_300 }` ;
- entonnoir : `{ id, canal, variante, froid, envoye_le, repondu, oui, appel, vente }` (`vente` peut valoir `null`).

Modules purs : syntaxe effaçable seulement, car le juge les importe par `scripts/ts-loader.mjs`. Aucun import hors `lib/pilotage/`.

## Ce qu'il faut faire

1. **`lib/pilotage/envois.ts`** :
   - `SEUILS_SANTE = { plaintes7j: 0, avisAbus: 0, stop100: 3, echecsAffilee: 3 }`, avec en commentaire la source (voie gratuite du 25/09, §2 et §3.2) ;
   - `compteur(utilises, plafond)` → `{ texte, plein, reste }` : `texte` « 12/15 » ; `plein` quand `utilises ≥ plafond` ; plafond `0` → « 0/0 », plein ; plafond `null` → « 12 / plafond non réglé », **plein** (prudent : la base refusera de toute façon) ;
   - `santeCanal(c)` → `{ etat: 'vert' | 'rouge' | 'inconnu', raisons: string[] }` : `vert` seulement si 0 plainte et 0 avis d'abus, au plus 3 STOP sur les 100 derniers envois, moins de 3 échecs de soumission d'affilée, et au moins une réponse positive à partir de P3 ; `rouge` dès qu'un seuil est dépassé, avec une raison lisible par seuil (« 4 STOP sur les 100 derniers envois ») ; `inconnu` quand l'un des compteurs vaut `null` et qu'aucun autre n'est rouge ; **jamais `vert` par défaut** ;
   - `envoisDesAgents(lignes, canaux, technologies, maintenant: Date)` → `{ palier, parCanal, parTechnologie, envois, rejets, anomalies, vide }` :
     - `palier` : le palier du canal `formulaire_site` (`'P0'` … `'P4'`), `null` si inconnu ;
     - `parCanal` : `{ canal, libelle, ...compteur(utilises, plafond), sante: santeCanal(…) }` par canal ;
     - `parTechnologie` : `{ technologie, envois, echecs_affilee, etat: 'active' | 'pause', pause_motif }` par technologie de formulaire (`envois` = `envois_jour`) ;

     - `rejets` : le nombre d'envois du jour dont au moins un verdict est `'refus'` (la zone REJET de la carte) ;
     - `anomalies` : `{ id, raison: 'verdicts_incomplets' }` pour chaque envoi `envoye` du jour qui n'est pas `complet` ;
     - `vide` : « Aucun envoi à froid : le canal formulaire s'ouvre au plus tôt le 12/10, après la mesure à sec, l'épreuve de bout en bout et l'ouverture par Benj. » quand le plafond de `formulaire_site` vaut 0 ou manque et qu'aucun envoi froid n'est du jour, sinon `null` ;

   - `HYPOTHESES = { reponse: { min: 0.01, max: 0.05, source: 'rectification du 24/09, §3.6 (supposé)' }, oui: { min: 0.03, max: 0.08, source: 'plan du 24/09, §1.5 (supposé)' }, achat: { min: 0.10, max: 0.25, source: 'plan du 24/09, §1.5 (supposé)' } }` ;
