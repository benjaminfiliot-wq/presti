`a2c110b3a3f90bf18419cabeae65a0bbfa3e73939bfd2e1cd06466e3f2e5383b`, exécuté en un seul `do $essai_026$ … end

Isolé hors du bloc d'essai (`create extension if not exists pg_cron;` seule, en tête de connexion, exécutée pour
de vrai — un IF NOT EXISTS sur une extension déjà installée ne devrait rien faire) : **la même erreur 2BP01**,
reproductible à volonté. `create extension if not exists pg_net;` seule : aucune erreur (no-op confirmé).

Diagnostic en lecture (confirme et affine celui du premier essai) :

```sql
select c.relname, c.relacl from pg_class c join pg_namespace n on n.oid=c.relnamespace
 where n.nspname='cron' and c.relname in ('job','job_run_details');
```

```
job              : {supabase_admin=arwdDxtm/supabase_admin,=r/supabase_admin,postgres=r*/supabase_admin,postgres=r/postgres}
job_run_details  : {supabase_admin=arwdDxtm/supabase_admin,=rd/supabase_admin,postgres=a*r*w*d*D*x*m*/supabase_admin,postgres=arwdDxm/postgres}
```

`postgres` porte deux octrois SELECT sur `cron.job` : un avec option de transmission (`r*`, consenti par
`supabase_admin`) et un sans (`r`, consenti par `postgres` lui-même). Le script de (ré)installation interne de
pg_cron tente un `revoke all on table cron.job from postgres;` qui doit défaire les deux à la fois ; Postgres
refuse sans `CASCADE` parce que le premier (`r*`, avec option) a peut-être des privilèges dépendants accrochés
ailleurs — exactement le diagnostic déjà posé le 24/09 et reconfirmé aujourd'hui, **inchangé malgré le geste
Extensions → désactiver/réactiver annoncé comme fait**.

## Décision

**Ne PAS corriger moi-même** l'ACL de `cron.job` : un `revoke ... cascade` sur un rôle aussi large que `postgres`
peut retirer des privilèges dont dépendent d'autres objets que je n'ai pas tous inventoriés (« dependent
privileges exist » le dit explicitement) — c'est un geste de sécurité sur la base réelle, hors du périmètre
d'une migration 026-086 et hors de ce que je dois trancher seul. Fiche laissée **BLOQUÉE**, non déplacée en
fait/, aucun commit.
