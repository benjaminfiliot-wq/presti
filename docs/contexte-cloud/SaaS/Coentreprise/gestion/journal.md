## 2026-09-05 — presti-gestion-fiabilite + presti-mails-delivrabilite (auditeur F) — Les tuyaux existent, l'alerte n'est pas garantie le jour où ça casse
- Contexte : audit final v6, périmètre crons / alertes / emails / bornes / observabilité / sauvegardes ; 0 appel IA, Stripe non touché, Vercel et Resend en lecture seule, ronde à sec, 0 compte de test créé. Rapport : `plans/audit-final/fiabilite.md` (0 bloquant, 12 majeurs, 14 mineurs, ≈ 9 h).
- Constat : 401 fail-closed sur les 4 routes cron (prod), crons actifs sur le déploiement courant, verrous atomiques vivants (107 créneaux, 5 RPC), domaine Resend `verified` (DKIM + SPF TXT/MX `send`), adresse d'alerte = `EMAIL_ENTREPRISE` sur Vercel, 8 motifs simulés hier tous `delivered`. Mais : **`passages_cron` absente en prod** (0057 non posée → `cron_muet` mort-né, `console.error` à chaque passage) ; `signalerPanneIA` lancé en `void` juste avant le `return` sur 10 sites et verrou 1 h consommé **avant** l'envoi (`alerteService.ts:69-72`) ; même ordre verrou→envoi dans la ronde (`alertes.ts:240`) et aucun canal hors Resend ; alerte « erreurs » = fenêtre 10 min à 08:00 sur une table que seul le navigateur remplit (`app_errors` = 0 ligne) ; relance dont l'email échoue marquée envoyée (`relances/route.ts:76-94`) ; alerte crédits quotidienne hors préférences ; **aucune borne globale d'emails** (6 leads/10 min/IP × 2 emails → 100/jour Resend gratuit en ~1 h 30) ; **34 % de rebonds** sur les 100 derniers envois (suites → `@presti-test.invalid`) ; DMARC `NXDOMAIN` ; `artisan-media` sans quota par compte ; démo = vrai compte Signature relancé par le cron sans filtre test ; aucune sauvegarde prouvée (offre Supabase illisible depuis le poste, 0 `pg_dump`).
- Décision / action : rapport chiffré, ordre : 0057 (2 min) → `await`/`waitUntil` + verrou après envoi → court-circuit `.invalid` + plafond `email:jour` → relances (résultat d'envoi, filtre test) → DMARC → crédits → `app_errors` serveur → quota stockage → `pg_dump` nocturne.
- À retenir : (1) sur Vercel Fluid, tout travail lancé après la réponse (`void promesse`) n'est pas garanti — `await` ou `waitUntil`, surtout pour une alerte ; (2) un verrou « une fois par jour » doit se consommer **après** un envoi réussi, sinon la panne du canal efface l'alerte ; (3) une alerte « cron muet » portée par le cron qu'elle surveille ne vaut que si un second déclencheur (GitHub Actions) l'appelle aussi ; (4) ne jamais faire partir par Resend un email vers `.invalid` : c'est un rebond dur qui note le domaine — court-circuiter dans `sendEmail` ; (5) vérifier une migration **en base** (PostgREST « Could not find the table ») avant de croire une alerte qui en dépend ; (6) `.env.local` n'a pas `CRON_SECRET` : les passages de cron ne se rejouent pas depuis le poste, l'idempotence se prouve par le code et l'état de la base.
