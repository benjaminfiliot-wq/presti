## Contexte

La migration 0096 (fiche 05) a posé le schéma `ops`. Il est fermé à tous, `service_role` compris, et compte 11 tables : `agents`, `taches`, `evenements` (ajout seul, purge seulement sous `ops.purge = 'oui'`), `decisions`, `prospects`, `envois`, `opposition`, `maquettes`, `quotas_canaux`, `couts` et `interrupteurs`. Les graines sont les agents `systeme` et `a0`, et l'interrupteur `pause_generale` à `false`.

On n'y entre que par des fonctions du schéma `public`, `SECURITY DEFINER`, exécutables par `service_role` seul. Le modèle est `supabase/migrations/0051_slug_modifiable.sql:33-42`.

La règle du journal est celle du Poste : « une écriture qui ne peut pas être journalisée n'a pas lieu » (`lib/direction/journal.ts:7-9`). Ici, chaque fonction d'écriture insère sa ligne dans `ops.evenements` **dans la même transaction** que l'écriture. Soit les deux tiennent, soit aucune.

Réservée à Claude Code : droits et schéma (`CLAUDE.md:23`).

## Contrat (recopié dans `contrat-ops.json`)

Toutes les fonctions sont `public.<nom>` et `security definer`, avec `set search_path = ops, public, pg_temp`, `revoke all … from public, anon, authenticated` et `grant execute … to service_role`. Une erreur métier se lève par `raise exception using message = 'ops:<code>', errcode = 'P0001'`.

## Ce qu'il faut faire

1. **`0097_ops_identite.sql`** : seulement les douze `create or replace function` du contrat, leurs `revoke` et `grant`, et des `comment on function`. Aucune table, aucune politique, aucun `grant` à `anon` ni à `authenticated`. Aucune fonction n'accepte un nom d'agent pris dans un texte libre : c'est l'appelant serveur qui le passe, tiré du jeton (fiche 10).

   - `proconfig` contient le `search_path` ;
   - `has_function_privilege('anon'|'authenticated', …, 'execute')` est faux ;
