## Contexte

Les agents extérieurs à Vercel passent par `/api/agents/*` (plan §3.2, fiche 11) : les routines Claude de la phase 3, le chef d'opérations sur Codex (GPT-6 sol, décision du 24/09) et les scripts locaux comme `pont-orchestre.mjs`. Le plan exige un jeton par agent, avec cinq propriétés :
1. **haché en base** (`ops.agents.jeton_hash`, sha256 hexadécimal, migration 0096) ;
2. **limité à ses types de tâches** (`types_crees`) **et à ses tables** (`tables_ecrites`) ;
3. **limité en débit** (`debit_minute`) ;
4. **journalisé** ;
5. **jamais la clé du produit** : ni `ANTHROPIC_API_KEY`, ni une clé Stripe, ni la clé de service.

Les agents qui tournent **dans** Vercel (A0 et la file de l'argent, appelés par le tic) n'ont pas de jeton : ils appellent `lib/agents/bus.ts` directement.

**Ce qui existe.**
- **`lib/limites.ts:19-28`** : `consommerLimite` laisse **passer** quand la base ne répond pas (`:15-17`, « fail-open assumé »). C'est juste pour un prospect du site, faux pour un agent. La garde appelle donc elle-même la fonction SQL `consommer_limite(p_cle, p_max, p_fenetre_s)` (migration 0049) et **refuse** si l'appel échoue.
- **`lib/supabaseAdmin.ts:8-10`** : le client serveur.
- **Le journal** : chaque écriture réussie est journalisée par la fonction SQL elle-même, dans la même transaction (fiches 06 et 07). Il reste à journaliser les refus d'un agent connu.
- **Le contrat SQL** : 0097 et 0098, dans `scripts/fixtures/026-horloge-bus/contrat-ops.json`. Les fonctions utiles ici :
  - `ops_agent_par_jeton(p_hash)` rend `nom`, `capacites`, `types_crees`, `tables_ecrites`, `debit_minute`, `en_pause` et `disjoncteur_ouvert` ;
  - `ops_agent_poser_jeton(p_nom, p_hash)` ;
  - `ops_evenement_ajouter(p_agent, p_type, p_objet, p_resume, p_tache)`.
- **Les erreurs métier** arrivent par PostgREST avec le message `ops:<code>`.

Réservée à Claude Code : droits (`CLAUDE.md:23`). **Les moteurs de modèle (`lib/agents/llm.ts`, 026-043 : Codex et freellmapi, sans clé) ne sont pas dans cette fiche** : la fiche 026-043 les porte, et aucun fichier d'ici ne les importe.

## Ce qu'il faut faire

1. **`lib/agents/jetons.ts`**, pur, sans réseau ni base :
   - `FORMAT_JETON = /^pa_([a-z0-9_]{2,40})_([A-Za-z0-9_-]{43})$/` ;
   - `genererJeton(nom)` : 32 octets de `crypto.randomBytes` en base64url ;
   - `empreinteJeton(jeton)` : sha256 hexadécimal du jeton entier ;
   - `nomDuJeton(jeton)` : le nom, ou `null`.
2. **`lib/agents/bus.ts`** : une fonction typée par fonction SQL des contrats 0097 et 0098, dont les paramètres portent **exactement** les noms `p_…` du contrat. Chacune rend `{ ok: true, data }` ou `{ ok: false, code, status }`.
   - La table `STATUT_ERREUR` fait correspondre `ops:<code>` et statut HTTP :

     | Statut | Codes |
     |---|---|
     | 400 | `options`, `defaut`, `echeance`, `choix`, `resume`, `preuve`, `jeton_format`, `purge`, `type_argent`, `vt` |
     | 403 | `type`, `auteur`, `opposition`, `capacite` |
     | 404 | `agent_inconnu`, `origine`, `interrupteur` |
     | 409 | `profondeur`, `sous_taches`, `bail_perdu`, `deja_tranchee`, `jeton_deja_pris`, `statut`, `90_jours`, `72_heures`, `3_messages`, `relance_sans_contact` |
     | 423 | `agent_en_pause`, `pause_generale`, `quota_absent` (canal fermé) |
     | 429 | `quota` |
     | 503 | base injoignable |
     | 500 | tout le reste, avec un message générique |

   - Le texte brut de l'erreur Postgres ne sort jamais de `bus.ts`. Il va seulement dans `console.error`.
3. **`lib/agents/garde.ts`** :
   - `authAgent(req)` rend `AgentAuth` (`nom`, `capacites`, `typesCrees`, `tablesEcrites`, `debitMinute`) ou `RefusAgent` (`status`, `code`, `error`). Dans cet ordre :
     1. un plafond par réseau IP, sur les jetons absents ou mal formés : clé `agents:ip:<reseauIp>`, 30 essais par 10 min (`reseauIp` de `lib/audienceServeur.ts:31`). La fonction SQL est appelée directement ; un échec de l'appel donne 503 ;
     2. l'en-tête `Authorization: Bearer <jeton>` au format ; sinon 401 `jeton`, avec le même corps pour « absent », « mal formé » et « inconnu », pour ne rien apprendre à qui essaie ;
     3. `ops_agent_par_jeton(empreinte)`. Aucune ligne → 401 `jeton`. Le nom lu dans le jeton diffère du nom rendu → 401 `jeton`. Erreur → 503 ;
     4. `en_pause` ou disjoncteur ouvert → 423 `agent_en_pause` ;
     5. `consommer_limite('agent:<nom>:minute', debit_minute, 60)`. `false` → 429 ; erreur → 503.
   - `exigerType(agent, type)` et `exigerTable(agent, table)` rendent `null` ou un refus 403. Chaque refus 403 ou 429 d'un agent connu écrit un événement `refus` par `ops_evenement_ajouter`, avec l'agent, le motif et la route. Le résumé ne contient ni le jeton, ni son empreinte, ni le corps de la requête. Si le journal échoue, le refus tient quand même.
   - `reponseRefusAgent(r)` rend une `NextResponse` JSON.
4. **`scripts/agents-jeton.mjs <nom> [--rotation] [--sortie=tube]`** (`--sortie=tube` : contre-revue du 25/09 au soir ; le jeton seul sur la sortie standard, suivi de `\n`, aucun autre texte ni consigne ; refus en code 2 si `process.stdout.isTTY`, **avant** toute écriture en base) :

   - il affiche le jeton **une seule fois**, avec la consigne : « à poser dans le coffre de l'agent ; il ne sera plus jamais affiché » ;
   - il n'écrit aucun fichier. Agent inconnu → code 1. Un jeton ne se crée que pour un agent déjà enregistré : `systeme` et `a0` (graines de 0096), les agents opérationnels semés par 0105 (`chef`, `pont`, `recenseur`… : 026-060), ou un `essai_e2e_…` d'une suite. Le script n'enregistre jamais un agent lui-même : c'est la migration qui fixe ses types, ses tables et son quota.
5. **Ne pas faire.** Ne pas modifier `lib/limites.ts` : son comportement est juste pour les prospects. N'importer ni `lib/agents/llm.ts`, ni `lib/stripe.ts`, ni aucune clé Anthropic. Aucune route dans cette fiche.
