# 014-13 — l'e2e de la validation des sites (`/api/controle/sites`)

## Ce que tu testes (les routes existent, ne les modifie pas)

- `GET /api/controle/sites?etat=<etat>&limite=50` → `{ commandes: [...] }` (jamais les brouillons ; chaque commande porte `artisan: { id, nom, metier, slug } | null`). Garde : `estFondateur` + domaine `clients` verbe `voir` (direction **et** lecture y ont droit).
- `POST /api/controle/sites/<id>` `{ action: 'valider' | 'regenerer', consigne? }` : `valider` = `generee → validee` (pose `valide_le`) ; `regenerer` = `generee → payee` (consigne ≥ 10 signes obligatoire → sinon 400 ; `regenerations + 1`, `genere_le/scores/verifications` remis à null). Depuis un autre état → 409. Direction seulement (verbe `ecrire` : le rôle lecture → refus). Chaque geste écrit une ligne `journal_direction` (`action = site_valide | site_regeneration`, `cible_type = site_commande`, `cible_id = <id>`) — et si le journal ne s'écrit pas, le geste est refusé.
- Sans jeton → 401 ; identifiant non-UUID → 400 ; commande inconnue → 404.

## Comment tu écris la suite

Copie le harnais de `scripts/controle-apports-e2e.mjs` (en-tête « ce qu'elle prouve », lecture de `.env.local`, `rest()`/`admin()` sur Supabase avec la clé service, création des comptes `sites-<nom>-<st>@presti-test.invalid` avec `is_founder` pour le fondateur et `direction_roles` pour un rôle `lecture`, `session()` + `verifierSessionTest`, compteur `T()`, purge en `finally`, `process.exitCode`). Les lignes `sites_commandes` de test : insérées directement par la clé service (une en `payee`, une en `generee` avec `scores` factices, une en `validee`), rattachées à un artisan de test, supprimées à la fin. **Aucune donnée réelle, aucun appel IA, aucun paiement.**

Ce qu'elle prouve, dans l'ordre :
1. `GET` par la direction liste les trois commandes de test, pas de brouillon ; `?etat=generee` n'en rend qu'une.
2. `POST valider` sur la `generee` → 200, état `validee`, `valide_le` posé, une ligne de journal `site_valide` avec `cible_id`.
3. `POST regenerer` sans consigne → 400 ; avec consigne → 200 sur une autre `generee` (crée-la), état `payee`, `regenerations = 1`, `consigne` gardée, journal `site_regeneration`.
4. `POST valider` sur la `payee` → 409 ; sur un UUID inconnu → 404 ; sur `abc` → 400 ; sans jeton → 401.
5. Le rôle `lecture` : `GET` → 200, `POST` → 403.

Cible : `TEST_BASE` (défaut `https://prestiapp.fr` — les routes doivent y être déployées ; en local `TEST_BASE=http://localhost:3000`). Code de sortie 0 si tout passe, 1 sinon, 2 si le drapeau `direction` est baissé sur la cible.
