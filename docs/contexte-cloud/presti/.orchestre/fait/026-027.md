## Contexte

Après un achat public, la fiche 09 envoie à l'acheteur un lien `https://prestiapp.fr/connexion/lien?th=<hashed_token>&commande=<id>`. Encore faut-il qu'il ouvre une session utilisable. Le code actuel l'empêche, et c'est voulu :
- toute route de Presti refuse une session qui ne figure pas dans `sessions_verifiees` (`lib/authArtisan.ts:92-99` et `:128`) ;
- une session n'y entre qu'après le code par e-mail (`app/api/auth/code/verifier/route.ts:68-73`, `marquerSessionVerifiee` dans `lib/connexion.ts:76-82`) ;
- les moyens permis sont `code_email`, `appareil` et `service` (`lib/connexion.ts:70`, contrainte de `supabase/migrations/0063_code_connexion.sql:31`).

Le lien reçu par e-mail prouve la même chose que le code : l'accès à la boîte. La session qu'il ouvre est donc marquée `code_email`. **La 2FA n'est jamais contournée** : `mfaManquante` est jugée avant le code (`lib/authArtisan.ts:127`), et un compte qui a une application d'authentification devra toujours la passer.

Deux dangers sont traités ici :
- **les robots de messagerie**, qui ouvrent les liens et en exécutent parfois le JavaScript. Le jeton n'est donc consommé que par un `POST`, après un clic ;
- **le rattachement d'une commande à un compte** : il ne se fait que pour la même adresse, prouvée par la session, jamais pour un compte fondateur (règle de `app/api/site/commander/route.ts:32-33`).

Réservée à Claude Code : droits et sessions (`CLAUDE.md:23`). Dépend de la fiche 09 et de la fiche 05 (colonne `rattachee_le`).

## Ce qu'il faut faire

1. **`POST /api/auth/lien`** `{ th }`, dans cet ordre :
   1. `isBanned` ;
   2. plafond `consommerLimite` de 20 par 10 min et par `ipPseudonyme` ;
   3. `th` doit être hexadécimal, de 20 à 128 signes ;
   4. `clientPublic().auth.verifyOtp({ token_hash: th, type })`, avec `type` égal à `'magiclink'` ou `'email'` selon ce qu'accepte `@supabase/supabase-js` 2.48 [à vérifier dans la documentation, et noter lequel dans le commentaire] ;
   5. en cas d'échec, 400 « Lien expiré ou déjà utilisé : demandez-en un nouveau », sans détail ;
   6. `sessionIdDuJeton(access_token)` puis `marquerSessionVerifiee(sid, uid, 'code_email')` (fonctions existantes de `lib/connexion.ts`, appelées, pas modifiées).

   Réponse : `{ ok: true, session: { access_token, refresh_token } }`, de la même forme que `app/api/auth/code/verifier/route.ts:73`. Pas de `GET`.
2. **`app/connexion/lien/page.tsx`** (client) :
   - elle lit `th` et `commande` dans l'adresse, mais **ne poste rien au chargement** ;
   - un bouton « Ouvrir mon dossier » poste `th`, puis `supabase.auth.setSession(session)` ;
   - elle redirige ensuite vers `/site/commander?commande=<id>`. C'est l'écran de la fiche 12 qui appelle `GET /api/site/commander/complement` (fiche 11), lequel rattache la commande par `rattacherCommandesParEmail`, et qui envoie vers `/onboarding?suite=/site/commander` si le profil n'existe pas encore ;
   - elle porte `noindex` et n'affiche jamais le jeton.
3. **`lib/siteAchatPublic.ts`** : `rattacherCommandesParEmail(uid, emailSession, deps)`.
   - Il rattache les commandes `achat_public`, sans compte, en `payee` ou au-delà, dont `lower(email)` égale `lower(emailSession)`.
   - Mise à jour conditionnelle `artisan_id is null` : pose `artisan_id = uid` et `rattachee_le`.
   - Si l'artisan est `is_founder` : aucun rattachement, et `notifierEntreprise` le signale.
   - Il rend la liste des commandes rattachées.

   Il ne prend jamais d'adresse venue du corps d'une requête.
