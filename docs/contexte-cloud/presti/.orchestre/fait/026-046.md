## Contexte

La migration 0100 (fiche 09) a créé la file durable `argent` (Supabase Queues, `pgmq`) et ses fonctions :

| Fonction | Rend | Effet |
|---|---|---|
| `ops_argent_envoyer(p_type, p_cle, p_charge, p_delai_s)` | `msg_id`, ou `null` si la clé est déjà connue | Met un message en file, une fois par clé |
| `ops_argent_lire(p_vt_s, p_n)` | les messages visibles, avec `msg_id`, `lectures`, `type`, `cle`, `charge`, `mis_le` | Lecture sous délai d'invisibilité. Au-delà de 3 lectures, la base archive le message et écrit un événement `argent_abandonne` |
| `ops_argent_fait(p_msg_id, p_cle, p_resultat)` | `true` la première fois, `false` ensuite | Marque l'effet et supprime le message |
| `ops_argent_etat()` | un résumé | — |

Types permis par la base : `commande_payee` et `essai_e2e`.

**Pourquoi.** Aujourd'hui, une commande de site payée passe à `payee` par le webhook (`lib/siteCommandeServeur.ts:52-97`, états dans `lib/siteCommande.ts:27`). L'entreprise reçoit un e-mail, puis rien d'autre ne se passe sans Benj. Le livreur A4 (domaine livraison-tresor) prendra des tâches `livrer_site`. Cette fiche garantit que **chaque commande payée fait naître sa tâche de livraison une fois et une seule**, même si le tic ou la base tombent entre-temps (recherche R8).

**Pourquoi un balayage plutôt qu'une modification du webhook.** Le webhook est le code de l'argent (025-07 le touche). Relire les commandes `payee` toutes les minutes coûte une requête, rattrape tout ce qui a été manqué, et ne change pas une ligne de ce qui encaisse.

`lib/agents/bus.ts` (fiche 10) porte `ops_tache_creer(p_agent, p_type, p_cle, p_capacite, p_charge, p_origine, p_objet)`. La clé est idempotente : la tâche existante est rendue avec `creee = false`. L'agent `systeme` crée sans restriction de type. Les alertes passent par `envoyerAlertes([{ motif: 'paiement', a: 'entreprise', cle, sujet, corps }])` (`lib/alertes.ts:304-309`), avec un verrou d'une fois par jour et par clé (`:311-313`).

Réservée à Claude Code : argent (`CLAUDE.md:23`).

## Ce qu'il faut faire

1. **`lib/agents/fileArgent.ts`** exporte :
   - `HANDLERS` : un registre **fermé**, exactement `commande_payee` et `essai_e2e` :
     - `commande_payee(charge)` lit `sites_commandes.etat` pour `charge.commande_id`, sans rien écrire dans cette table. En `brouillon` ou introuvable : rien, résultat `{ ignore: '<raison>' }`. En `payee`, `generee`, `validee` ou `en_ligne` : `ops_tache_creer('systeme', 'livrer_site', 'livrer_site:<id>', 'livraison', { commande_id }, null, 'commande:<id>')`. Idempotent par construction ; **puis** (revue du 25/09), pour une commande `payee` seulement, `deposerEntreeUsine({ tache: <id rendu>, commande_id, essai: charge.essai === true })` ;
     - `deposerEntreeUsine(…)` (dans le même fichier) : si `usine/<tache>/entree/commande.json` existe déjà, rien ; sinon, avec `supabaseAdmin.storage.from('usine')` : `usine/<tache>/entree/commande.json` = la commande **au format `--depuis` de `scripts/commande-exporter.mjs`** (026-033 : ce que l'exporteur lit de la base pour cette commande, et rien de plus ; `essai: true` si la charge le porte), les photos du dossier de la commande copiées sous `usine/<tache>/entree/photos/` (mêmes fichiers que l'exporteur lit), et l'index `usine/commandes/<commande_id>.json` = `{ tache }` ; **au mieux** : toute erreur (bucket absent avant 0110, stockage refusé, photo introuvable) écrit un événement `entree_usine_absente` de `systeme` (sans donnée personnelle) et **ne fait jamais échouer le gestionnaire** : `ops_argent_fait` est appelé comme avant ;
     - `essai_e2e(charge)` écrit un événement `essai_e2e` et rend `{ ok: true }` ;
   - `traiterFileArgent({ budgetMs = 12000, lot = 5, vtS = 120, handlers = HANDLERS })` : boucle `ops_argent_lire(vtS, lot)` tant que le budget n'est pas épuisé. `vtS` est borné de 5 à 3600, comme dans la base. Pour chaque message :
     - type absent du registre : une alerte `paiement` de clé `argent:type_inconnu:<cle>`, et **pas** de `fait` : la base l'archivera à la 4e lecture ;
     - sinon le gestionnaire, sous un délai égal au reste du budget. Succès : `ops_argent_fait(msg_id, cle, resultat)`. Échec : rien ; le message revient après `vtS` secondes ;
     - plus aucune lecture dès que le budget est épuisé.

     Rend `{ lus, faits, echecs, inconnus, dureeMs }`. Le paramètre `handlers` sert aux suites.
   - `balayerCommandesPayees()` : les commandes `sites_commandes` en `payee` depuis 30 jours au plus (100 au plus). Pour chacune, `ops_argent_envoyer('commande_payee', 'commande_payee:<id>', { commande_id: id }, 0)`. Rend `{ vues, envoyees }`.
2. **Ne pas faire.**
   - Aucun import de `lib/stripe`, de `lib/email` ni de `lib/siteCommandeServeur`.
   - Aucun `update`, `insert` ni `delete` sur `sites_commandes` ou `artisans`.
   - Aucune écriture de stockage hors du bucket `usine` et des chemins `usine/<tache>/entree/**` et `usine/commandes/<commande_id>.json` ; aucune lecture de `usine/<tache>/sortie/` (c'est le consommateur, 026-141).
   - Pas d'e-mail à l'artisan : les trois e-mails de livraison appartiennent au livreur A4.
   - Pas de route : le tic (fiche 15) appellera ces fonctions.
