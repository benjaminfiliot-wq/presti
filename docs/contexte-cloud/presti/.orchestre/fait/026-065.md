## Contexte

**Dépend de :** 026-016, 026-019 et 026-020 PASS.

**Réservée à Claude Code** : J1 est un juge, la porte avant tout message. Aucun fait n'entre dans un message sans être passé par lui.

Pourquoi un juge qui relit tout : les agents fabriquent la preuve dès qu'on les laisse la déposer (trois fraudes le 13/09, trente comptes inventés le 15/09 : mémoire `juge-capture-lui-meme`). Le modèle existe : `scripts/emails-artisans-qa.mjs` retélécharge la page source et y cherche le texte en toutes lettres. Aucune adresse n'est plus vérifiée : il n'y en a plus (R4 = non).

**Indépendance.** J1 n'utilise de `lecteurSite.ts` que la politesse (`recupererPoli`, `robotsAutorise`) : il n'importe **ni** `extraire`, **ni** `lireSite`, **ni** `lireFormulaire`, et calcule lui-même le texte visible, sa normalisation et l'éligibilité du formulaire. Un défaut du Lecteur ne peut donc pas se valider lui-même.

## Ce qu'il faut faire

1. `executerJugeFaits(deps)`, `deps = { magasin: MagasinSocle, recuperer, horloge, echeance, jetonMeta: string | null }` (le jeton est lu par la route dans le coffre, `rpc('acq_jeton_meta')`, 026-077 ; `null` s'il n'est pas posé) ; `magasin.reserver('recense', 15, 300)`.
2. Par prospect : opposition revérifiée (`oppose`, aucune requête) ; `ficheParSiren` rappelée, qui doit toujours passer `retenir(resultat, prospect.cible)` (sinon `rejete` avec la raison).
3. `normaliserTexte(s)` : NFKC, entités décodées, apostrophes et guillemets typographiques ramenés à leur forme droite, trait d'union conditionnel retiré, espaces fusionnés. `texteVisible(html)` écrit ici, indépendant d'`extraire`.
4. `verifierFait(fait, deps)` :
   - `site_*` : la page de `fait.url` est relue par J1 ; `ok` si `normaliserTexte(extrait)` est dans `normaliserTexte(texteVisible(page))`, sinon `absent` ; page illisible → `injoignable` ;
   - `pub_meta` : si `jetonMeta`, `ads_archive` interrogée par `search_page_ids=[page_id]` (hôte `graph.facebook.com`, chemin `/v26.0/ads_archive`) ; `ok` si l'annonce de même identifiant porte l'extrait dans ses titres ou ses textes, `absent` si la réponse est **valide** et que l'annonce ne le porte pas ; sans jeton → `non_verifiable` ;
   - **une erreur de l'API n'est jamais un `absent`** (revue du 24/09, B3) : 190 (jeton invalide ou expiré), 1357045 (identité), 4, 17, 32 ou 613 (débit), 5xx ou coupure → `non_verifiable`. Dès la première erreur, J1 cesse d'interroger Meta pour le reste de l'exécution (les faits `pub_meta` suivants sont `non_verifiable` sans requête) et le bilan porte `meta: 'jeton_invalide'` (190), `'en_attente_identite'` (1357045), `'limite'` (débit) ou `'injoignable'` ; la route signale les deux premiers comme un échec (026-077) ;
   - les faits d'audit (`site_http`, `site_mobile`, `site_copyright`) se relisent de même : l'URL servie sans HTTPS, l'absence de viewport, la mention « © AAAA » mot pour mot ;
   - chaque fait garde `verifie`, `verifie_le` et `empreinte_page` (SHA-256 du texte normalisé).
5. Canaux : Instagram et Facebook retrouvés sur leur `url_source` relue ; **le formulaire** (`formulaire_site`, prospect froid) relu par `verifierFormulaire(formulaire, deps)`, écrit ici : la page est relue ; le `<form>` porte la même URL d'action et la même technologie ; **aucune signature de protection** n'y apparaît (captcha, pot de miel, case « je ne suis pas un robot », question anti-spam, défi JS, pare-feu, extension anti-spam, refus du démarchage : une liste écrite ici, indépendante de `lireFormulaire`) ; robots.txt permet la page **et** l'action ; sinon le canal est retiré avec la raison `formulaire_<raison>`. **Aucune adresse n'est vérifiée ni gardée** hors celle qu'une personne a donnée elle-même (`donnee_par_la_personne`, un entrant), gardée telle quelle.
6. Verdict : `verifie` si SIREN retenu **et** au moins un fait `ok` **et** au moins un canal retrouvé (pour un prospect froid : le formulaire, toujours éligible) ; le patch ne garde que les faits `ok` ou `non_verifiable` et les canaux retrouvés. Sinon `rejete` avec la liste des codes (`aucun_fait_verifie`, `aucun_canal_verifie`, `formulaire_<raison>`, raison SIRENE). Écriture par `mettreAJour(id, 'recense', …)`. **Exception** : un prospect qui n'a aucun fait `ok` **parce que** ses faits `pub_meta` sont `non_verifiable` à cause d'une erreur de l'API pendant cette exécution n'est ni rejeté ni écrit : J1 ne l'écrit pas, son bail expire, et il sera repris à l'exécution suivante (au bout de 3 tentatives, `a_decider`, visible par Benj). Sans cette exception, un jeton expiré rejetterait pour toujours tous les prospects « Meta seulement ».
7. Bornes, politesse et bilan comme le recenseur (15, 45 s, un événement sans donnée personnelle). Le jeton n'est jamais écrit, affiché ni rendu.
8. **`verifierAvantEnvoi(envoi, prospect, deps)`** → `{ j1: 'ok' | 'refus' | 'injoignable' | 'sans_objet', raisons: string[] }`, appelé par le Facteur juste avant d'approuver (rectification §3.11 : « J1 : chaque fait est retrouvé mot pour mot dans sa source datée ») :
   - `envoi.type` autre que `premier_contact` → `sans_objet`, aucune requête (la seule relance qui reste est sollicitée, sans fait) ;
   - le fait `envoi.fait_id` du prospect est **relu maintenant** par `verifierFait` : `ok` exigé ; `absent` → `refus` (`fait_absent`) ; `non_verifiable` → `refus` (`fait_non_verifiable` : un fait qu'on ne peut plus prouver ne part pas) ; `injoignable` → `injoignable` (le Facteur remet l'envoi à plus tard, sans le refuser) ;
   - pour un `formulaire_site`, la page du formulaire (`envoi.destinataire`) est relue par `verifierFormulaire` : même URL d'action, même technologie, toujours éligible, robots.txt de la page et de l'action ; une protection apparue ou un robots.txt fermé → `refus` avec la raison `formulaire_<raison>` ; action ou technologie changée → `refus` (`formulaire_change`) ; page illisible → `injoignable` ;
   - un fait `pub_meta` (une `marque` du Studio) se relit par `ads_archive` avec `deps.jetonMeta` ; sans jeton → `refus` (`fait_non_verifiable`) ;
   - au plus trois requêtes par envoi (le fait, la page du formulaire, son robots.txt), avec la même politesse (robots.txt, 1 000 ms par hôte, `UA_RECENSEUR`) ; aucune écriture dans le magasin : c'est le Facteur qui enregistre le verdict ;
   - le verdict ne dépend jamais d'un texte produit par un modèle.

## Cahier du juge

Le juge (`faits-qa`) part des prospects `recense` de `candidats.json`, sert les pages d'essai **modifiées après le recensement** quand un cas l'exige, et lit l'état final du magasin factice.
- **JF-1** le module exporte `executerJugeFaits`, `normaliserTexte`, `texteVisible`, `verifierFait`, `verifierFormulaire`, `verifierAvantEnvoi`.
- **JF-2** substance : un extrait retouché d'un mot sur la page → `absent` ; exact → `ok` ; apostrophe courbe d'un côté, droite de l'autre → `ok` ; extrait présent seulement dans un `<script>` → `absent`.
- **JF-3** indépendance : le source n'importe ni `extraire` ni `lireSite` ; et le récupérateur factice enregistre une requête de J1 pour chaque `url` de fait, même déjà lue par A8.
- **JF-4** unité passée en diffusion P entre A8 et J1 → `rejete` avec `diffusion_partielle`.
- **JF-5** compte Instagram absent de sa page source (inventé) → retiré ; s'il était le seul canal → `rejete` avec `aucun_canal_verifie`.
- **JF-6** (réécrit par la voie gratuite) formulaire : le formulaire conforme relu tel quel → canal gardé ; la même page où un script reCAPTCHA est apparu depuis le recensement → canal retiré, `formulaire_captcha` ; robots.txt qui interdit désormais l'action → `formulaire_robots_txt` ; s'il était le seul canal d'un froid → `rejete` ; une adresse e-mail glissée dans le prospect (hors `donnee_par_la_personne`) → retirée et jamais écrite ; lecture du source : ni `resoudreMx`, ni `adressesNominatives`, ni `mailto`, ni import de `lireFormulaire`.
- **JF-12** (réécrit par la voie gratuite) `verifierAvantEnvoi` : une `reponse`, un `lien_maquette` ou une `relance` sollicitée → `sans_objet` et zéro requête ; un premier contact `formulaire_site` dont le fait est toujours sur la page et le formulaire toujours éligible → `ok`, trois requêtes au plus, toutes avec `UA_RECENSEUR` ; la page du fait retouchée d'un mot entre la vérification et l'envoi → `refus` avec `fait_absent` ; un hCaptcha apparu sur la page du formulaire → `refus` avec `formulaire_captcha` ; l'URL d'action changée → `refus` avec `formulaire_change` ; le robots.txt qui interdit l'action → `refus` avec `formulaire_robots_txt` ; le fait `pub_meta` d'une marque sans jeton → `refus` avec `fait_non_verifiable` ; page en 500 → `injoignable`, jamais `refus` ; aucune écriture du magasin factice pendant ces appels.
- **JF-7** fait `pub_meta` sans jeton → `non_verifiable`, et le prospect est `verifie` s'il a un fait de site `ok` ; avec le jeton `JETON-TEMOIN-7f3a` et un texte d'annonce changé → `absent` ; ce jeton n'apparaît dans aucune écriture du magasin, aucun événement, ni la sortie console capturée.
- **JF-11** jeton Meta refusé (le récupérateur factice rend l'erreur 190 à la première requête `ads_archive`) : le fait `pub_meta` est `non_verifiable`, jamais `absent` ; un prospect qui a aussi un fait de site `ok` est `verifie` et garde son fait `pub_meta` ; un prospect « Meta seulement » n'est ni `rejete` ni écrit (aucun `mettreAJour` pour lui) ; une seule requête Meta part pendant toute l'exécution ; le bilan porte `meta: 'jeton_invalide'` ; même chose avec 1357045 (`en_attente_identite`) et 613 (`limite`), chacun avec son état dans le bilan.
- **JF-8** prospect mis en opposition entre A8 et J1 → `oppose`, zéro requête.
- **JF-9** 20 prospects en file → 15 au plus traités ; arrêt avant l'échéance virtuelle ; au moins 1 000 ms entre deux requêtes au même hôte.
- **JF-10** lecture du source : aucun `process.env` (ni `META_ADLIB_TOKEN`, ni `ACQ_ADRESSES_NOMINATIVES`), aucun import interdit ; `npm run typecheck` vert.
